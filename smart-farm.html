Project 02 · Smart Farm Case Study

센서 데이터를
확인과 대응의 흐름으로.

스마트팜 전문가 양성과정 조별 프로젝트에서 ICT 담당으로 참여해 장치·통신·웹을 연결하고, 실제 측정값과 원격 제어 결과를 단계별로 검증했습니다.

01 · Overview

장치 앞에 있지 않아도 상태를 이해할 수 있게

센서값이 Arduino와 PC 안에 머물면 다른 장소에서 상태를 확인하거나 명령을 전달하기 어렵습니다. 수집·전달·시각화·알림·제어를 하나의 운영 흐름으로 연결했습니다.

MONITOR

실시간 상태

온도·습도와 수신 시각을 카드와 그래프로 확인합니다.

NOTICE

정시·경고 알림

Telegram으로 시간 단위 요약과 기준 이탈 경고를 받았습니다.

CONTROL

원격 명령

웹의 ON/OFF 명령을 MQTT로 전달해 실제 LED 반응을 확인했습니다.

02 · Problem & User

수치가 아니라 운영자가 판단할 정보를 보여줘야 했습니다

TARGET USER

현장을 확인하는 운영자

장치와 떨어진 곳에서도 현재 상태, 데이터가 마지막으로 들어온 시점, 기준 이탈 여부를 빠르게 알고 싶은 사용자입니다.

CORE PROBLEM

분리된 장치와 화면

센서값, 제어 명령, 알림이 따로 존재하면 상태 판단과 대응에 시간이 걸리고 연결 장애도 알아차리기 어렵습니다.

핵심 질문

“지금 데이터가 정상적으로 들어오고 있으며, 기준을 벗어났을 때 어디서 확인하고 어떻게 대응할 것인가?”

04 · Functional Requirements

기능과 상태 기준을 구체화했습니다

FR-01연결 상태브로커 연결·실패·재연결 상태를 구분하고 사용자가 현재 상태를 알 수 있게 표시
FR-02실시간 센서 카드온도·습도 값, 단위, 적정 상태와 마지막 수신 시각 표시
FR-03추세 그래프최근 데이터 흐름을 유지해 순간값이 아닌 변화 방향 확인
FR-04원격 제어ON/OFF 명령 발행과 수신 결과를 구분해 표시
FR-05자동 알림정시 상태 요약과 기준 이탈 경고를 Telegram으로 전달
FR-06모바일 접근GitHub Pages HTTPS 환경에서 WSS로 연결하고 작은 화면에서도 카드와 제어 사용

05 · Key Decisions

연결 여부와 검증 범위를 숨기지 않았습니다

마지막 수신 시각 표시값이 정상 범위여도 오래된 데이터일 수 있으므로 수치와 함께 데이터 신선도를 판단하게 했습니다.
HTTPS에서는 WSS 사용GitHub Pages의 보안 정책에 맞춰 HiveMQ WebSocket TLS 포트와 경로를 사용했습니다.
중계 경로와 직접 경로 비교Raspberry Pi 5·Node-RED 중계 구조를 구성한 뒤 Arduino가 HiveMQ Cloud에 직접 연결되는 경로도 별도로 시험했습니다.
검증 결과와 UI 확장 구분대시보드에 펌프·EC·pH 기능을 설계했지만 실제 하드웨어로 검증하지 않은 항목은 성과로 주장하지 않습니다.

06 · Implementation

장치와 서비스 사이의 흐름을 직접 연결했습니다

01 · DEVICE

Arduino UNO R4

DHT11 측정·LED 명령 수신

02 · EDGE

Raspberry Pi 5

Node-RED·Tailscale 원격 관리

03 · MESSAGE

HiveMQ Cloud

MQTT/TLS와 WebSocket 전달

04 · SERVICE

Web + Telegram

모니터링·명령·정시·경고 알림

기술 세부와 장애 해결 기록 보기
  • UNO R4 WiFi가 5GHz에 연결되지 않아 2.4GHz SSID로 변경했습니다.
  • MQTT `rc=-2` 반복 시 일반 WiFiClient 대신 WiFiSSLClient와 TLS 8883을 적용했습니다.
  • 펌웨어 갱신 후 USB 포트가 변경된 문제를 새 포트 선택으로 해결했습니다.
  • Raspberry Pi 무선 재연결과 사설 IP 변경 문제에 Tailscale 원격 경로를 사용했습니다.
  • HTTPS 페이지의 `ws` 차단 문제를 HiveMQ `wss:8884/mqtt`로 해결했습니다.

07 · Validation

실제 확인한 것과 확인하지 않은 것을 분리합니다

검증 기준

화면에 값이 보이거나 명령 로그가 찍힌 것만으로 실물 동작 성공을 주장하지 않았습니다. 센서 실측값과 물리 장치 반응을 기준으로 구분했습니다.

  • DHT11 실제 온도·습도 측정
    Arduino 시리얼 로그와 대시보드 값 갱신 확인    VERIFIED
  • 웹 ON/OFF → 실제 LED 점등·소등
    Arduino·브레드보드·LED를 연결해 물리 반응 확인    VERIFIED
  • Telegram 정시 요약·기준 이탈 경고
    조별 프로젝트의 자동화 흐름에서 메시지 수신 확인    VERIFIED
  • Raspberry Pi 5·Node-RED·Tailscale 운영
    교육 프로젝트에서 실제 연결·원격 관리 경로 구성    VERIFIED
  • 펌프 물리 작동
    명령 토픽과 UI는 설계했지만 실제 펌프 하드웨어 미연결    NOT VERIFIED
  • EC·pH 실제 센서값
    카드와 토픽은 확장했지만 센서 하드웨어 미보유·미검증    NOT VERIFIED

08 · Reflection

기술 연결보다 운영자가 믿을 수 있는 상태가 중요했습니다

LEARNED

오류는 계층별로 좁혀야 했습니다

Wi-Fi, TLS, MQTT 인증, WebSocket, 브라우저 보안과 물리 배선을 한 번에 보지 않고 각 단계의 로그와 결과를 대조했습니다.
